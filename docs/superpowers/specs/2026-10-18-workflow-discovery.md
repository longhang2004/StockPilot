# StockPilot workflow redesign discovery

Date: 2026-10-18. Repository revision inspected: readiness review says local and remote `main` were `312eee9ed383fb293273c989b8a00a4ed43903b6`; local source inspection was performed in the shared workspace.
Purpose: map the smallest implementation surface for closing the operational workflow gaps while redesigning the workspace around an SAP Fiori inspired worklist, list report, and object page.

## Findings at a glance

| Workflow                        | What already exists                                                                                                                                                                                                               | What is missing                                                                                                                                                                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actionable exceptions           | `/dashboard/overview` counts open low-stock alerts, Draft orders, and failed deliveries. `/alerts` and `/integration-deliveries` already return item rows; orders are searchable and filterable.                                  | Overview receives counts only. It cannot show the affected SKU/order/delivery, reason, age, or direct object action. A composed worklist response or parallel bounded queries is needed.                                                           |
| Draft edit and deep links       | `GET /orders/:id`, `PATCH /orders/:id`, order detail includes lines and transitions, list supports `search`, `status`, `page`, `pageSize`. Update serializes with transitions and returns `409` if the order stopped being Draft. | The UI only creates Drafts. Search/status/page/selection live in React state, so they do not survive reload or Back/Forward. Detail is a drawer with Confirm/Cancel only.                                                                          |
| Lost-response Draft create      | The client already has a `useCommandMutation` pattern and the API has transaction-backed `executeIdempotent`; order transitions, receipts, and adjustments use it.                                                                | `POST /orders` has no idempotency header, and the create drawer calls ordinary `useMutation`. A lost successful response followed by resubmission can create a second Draft.                                                                       |
| Receipt documents               | `POST /receipts` accepts a supplier, receipt number/date, note and lines; its result includes document and line IDs, supplier ID, quantities and unit costs. Movement ledger can filter `type=RECEIPT`.                           | There is no `GET /receipts` or `GET /receipts/:id`. The receipts screen lists individual movements, not documents, and cannot display supplier/reference/complete document lines.                                                                  |
| SKU reservation and audit trace | Balance includes on-hand/reserved/available. Confirmed order lines can be joined to SKUs; SALE and RECEIPT movements carry `referenceType/referenceId`; audit list returns `entityType/entityId` and before/after.                | Balance has no orders responsible for its `reserved` total. Confirming/cancelling a Draft changes reservation and audit but emits no stock movement; a dedicated reservation source query/view is needed. Frontend has no source/audit deep links. |

The existing data model can support these flows without changing the inventory invariants. Keep reservations derived from the balance projection and order status; do not pretend a reservation is a movement. Make the source order and its audit trail discoverable alongside the aggregate reservation.

## Exact current endpoints and data shapes

### Overview and exceptions

- `GET /v1/dashboard/overview`, permission `inventory:read`: `apps/api/src/dashboard/dashboard.controller.ts:17-21`. `DashboardService.overview()` computes exception counts at `apps/api/src/dashboard/dashboard.service.ts:22-39` and returns only `failedIntegrations`, `openLowStockAlerts`, and `ordersAwaitingApproval` at `:87-92`. Shared `OverviewResponse` is a plain TypeScript interface (not runtime validated) at `packages/contracts/src/analytics.ts:6-10,34-45`.
- Current UI renders the counts as three summary cards and three generic work rows with module links, not affected records: `apps/web/features/overview/overview-workspace.tsx:99-124,126-168`.
- Existing concrete source APIs:
  - `GET /v1/alerts?status=OPEN&page=&pageSize=` at `apps/api/src/inventory/inventory.controller.ts:194-229`; rows include `productId`, `status`, `availableAtOpen`, `reorderPoint`, `openedAt`, `resolvedAt`, and product `{name,sku}` per `packages/contracts/src/inventory.ts:126-144`.
  - `GET /v1/integration-deliveries?status=FAILED&page=&pageSize=&search=` plus `GET /v1/integration-deliveries/:id` and retry at `apps/api/src/integrations/integration.controller.ts:74-103`. List filters/pagination are at `apps/api/src/integrations/integration.service.ts:116-160`. The raw model also stores `salesOrderId`; the public `IntegrationDeliveryRecordSchema` currently exposes id, externalDeliveryId, eventType, status, attempts, lastError, payload, createdAt, processedAt at `packages/contracts/src/integrations.ts:20-30` but omits `salesOrderId` and `updatedAt`.
  - `GET /v1/orders?status=DRAFT&search=&page=&pageSize=` at `apps/api/src/orders/orders.controller.ts:46-82`.
- Minimal actionable worklist design: retain counts but add small bounded item arrays under the overview response (for example `exceptionItems.lowStock`, `.draftOrders`, `.failedDeliveries`, each carrying stable ID, display identifier, reason/state and age timestamp), OR use existing paged APIs from Overview and cap each to a few rows. A single composed endpoint is better for a coherent request snapshot and reduces client orchestration. Do not invent reasons where source data is absent: failed delivery has `lastError`; low stock can show `availableAtOpen/reorderPoint`; Draft shows age/status and order/customer.
- Failure/handling actions already exist for some rows: open order detail then edit/confirm, open alert SKU and receive stock, open delivery detail and retry (retry uses idempotency). A low-stock alert is informational; receiving inventory affects its reconciliation status. The exact SAP worklist row can link into object page or the existing action route.

### Orders and Draft recovery

- `GET /v1/orders`: `page`, `pageSize`, `search`, `status` documented and parsed at `apps/api/src/orders/orders.controller.ts:46-82` and `apps/api/src/orders/orders-schemas.ts:8-13`. Search covers order number and customer company name at `apps/api/src/orders/order-query.service.ts:12-23`; sort is newest first at `:25-34`.
- `GET /v1/orders/:id` returns the order plus lines and transition timeline at `apps/api/src/orders/orders.controller.ts:84-97` and `apps/api/src/orders/order-query.service.ts:37-55`.
- `PATCH /v1/orders/:id` already accepts `SalesOrderInput` and returns full detail at `apps/api/src/orders/orders.controller.ts:112-132`. `OrdersService.updateDraft()` locks the order, checks Draft status, replaces lines and audits the update at `apps/api/src/orders/orders.service.ts:57-105`. This gives the UI a useful conflict response when another actor confirms during edit.
- Shared `SalesOrderInputSchema` contains `customerId`, unique product lines `{productId,quantity}`, and optional note at `packages/contracts/src/orders.ts:22-39`. Detail response includes customer snapshot, status, totals, line snapshots and transitions at `:45-99`.
- Current list/detail state is not URL-backed: `apps/web/features/orders/orders-workspace.tsx:38-70,143-185,214-241`. The URL is only read once for `new=1` and `status` (effect at `:48-59`). Selecting a row only calls `setSelectedId` (`:179`); closing clears local state (`:220`). `OrderDetailView` offers Confirm/Cancel for Draft and no edit entry at `apps/web/features/orders/components/order-detail-view.tsx:57-88`.
- `createDraftOrder()` sends plain `POST /orders` without `Idempotency-Key` at `apps/web/features/orders/api.ts:17-22`; the API POST has no idempotency decorator/header at `apps/api/src/orders/orders.controller.ts:99-110`; service runs the normal create transaction at `apps/api/src/orders/orders.service.ts:30-39`. The UI uses a plain React Query mutation and discards its form after success at `apps/web/features/orders/components/order-form-drawer.tsx:63-76,94-99`.
- Reuse `useCommandMutation` for create. It stores the exact input/key in session storage, restores unknown outcomes, and blocks stale replay after its safe window (`apps/web/hooks/use-command-mutation.ts:10-18,19-36,38-71,96-149`). Server `executeIdempotent` is used by transitions at `apps/api/src/orders/orders.service.ts:109-131`; it stores response with command effects in the same transaction (implementation `apps/api/src/idempotency/idempotency.ts:28+`). Add an idempotent create scope and required header at POST. Preserve the submitted input until server result is known; avoid resetting the form on unknown outcome. `CommandIntentScope` is provided as `organizationId:userId` by `apps/web/components/app/workspace-shell.tsx:70-79`.

### Receipts, balances, movements, reservations, and audit

- Current receipt command: `POST /v1/receipts` requires `inventory:receive`, CSRF/session write and `Idempotency-Key`; route is `apps/api/src/inventory/inventory.controller.ts:159-191`. It validates `ReceiptInputSchema` and atomically creates a `GoodsReceipt`, lines, balance changes, ledger movement and audit event in `apps/api/src/inventory/receipt-command.service.ts:40-127`.
- `ReceiptInputSchema` fields: `supplierId`, `receiptNumber`, `receivedAt`, optional note, lines `{productId,quantity,unitCost}` at `packages/contracts/src/inventory.ts:23-43`. `ReceiptResultSchema` includes document fields, supplierId, receipt number/date/note, balances, and lines with goodsReceiptId/productId/quantity/unitCost at `:146-170`; it does not embed supplier/product labels.
- Current receipts page explicitly uses `GET /inventory/movements?type=RECEIPT` (`apps/web/features/receipts/api.ts:5-6`, `apps/web/features/receipts/receipts-workspace.tsx:37-42`) and renders each movement as a row at `:79-85,130-163`. This is one row per SKU movement, so a multi-line document is split. It does not include receipt number/supplier; the page has no selection state or detail view.
- Missing document API: paginated `GET /v1/receipts` filters such as `search` by receipt number/supplier, date range, and pagination; `GET /v1/receipts/:id` returns receipt header plus supplier brief, ordered lines plus product briefs, and linked movement/audit identifiers. Back it with `goodsReceipt` / `goodsReceiptLine`, scoped by organization and with deterministic order. Add shared response schemas to `packages/contracts/src/inventory.ts`, API query/service/controller/OpenAPI wiring, and web API types.
- Movement source keys already exist. `StockMovementSchema` has `referenceType`, `referenceId`, `productId`, quantityDelta, onHandAfter, actor and createdAt at `packages/contracts/src/inventory.ts:68-99`. Receipt writes `GOODS_RECEIPT` + receipt UUID (`apps/api/src/inventory/receipt-command.service.ts:85-97`); order fulfillment writes `SALES_ORDER` + order UUID (`apps/api/src/orders/order-transition.service.ts:104-116`). Link those to `/app/receipts?receipt=<id>` and `/app/orders?order=<id>` or selected object pages.
- Balance fields at `packages/contracts/src/inventory.ts:101-117` contain totals only (`onHand`, `reserved`, `available`, product and warehouse). Query computes available as onHand minus reserved at `apps/api/src/inventory/inventory-query.service.ts:18-47`.
- Confirming a Draft increments `inventoryBalance.reserved` by each order line but writes no movement (`apps/api/src/orders/order-transition.service.ts:40-68`). Fulfillment decrements reserved and on-hand and writes a SALE movement referencing the order (`:69-117`); cancelling confirmed orders releases reserved only (`:119-147`). To explain current reserved quantity, add `GET /inventory/balances/:productId/reservations` or embed `reservations[]` in balance detail, sourced from confirmed SalesOrderLines joined to SalesOrders where organization/product/warehouse match and status is CONFIRMED. Return order ID/number, customer, quantity, confirmedAt, line ID. This is a current-state explanation; audit history can explain changes over time.
- Audit source: `GET /v1/audit-events?entityType=GoodsReceipt&page=&pageSize=` requires `audit:read`; route/filter at `apps/api/src/audit/audit.controller.ts:10-25`; returned event has action, entityType/entityId, createdAt, actor display name, before/after at `packages/contracts/src/audit.ts:9-23`. It cannot currently filter entityId, so the minimal UI can link to an entity-filtered audit view but a direct per-document audit detail endpoint or entityId query parameter would be a useful API addition. For low-risk scope, add `entityId` filter in existing controller/service and preserve `audit:read` permission.
- Existing inventory UI already shows balance and low-stock alert tables (`apps/web/features/inventory/inventory-workspace.tsx:30-52,119-191,211-250`), but balance rows are not selectable and source trace is absent.

## URL and route APIs supported by installed Next.js

The app is App Router, client workspace components, and the local dependency docs are at `apps/web/node_modules/next/dist/docs/01-app/` (read before any implementation per `apps/web/AGENTS.md`). Relevant exact guides read:

- `03-api-reference/04-functions/use-router.md`: client import is `useRouter` from `next/navigation`; supported navigation includes `router.push(href)` (adds history entry), `router.replace(href)` (replaces), `router.back()`, and `router.forward()`. Recommendation is use `<Link>` for navigation unless imperative updates are needed. This supports filter edits with `replace`, detail open/close with `push`/`back`, and browser Back/Forward restoration. Avoid untrusted hrefs.
- `03-api-reference/04-functions/use-search-params.md`: `useSearchParams()` is a Client Component hook returning read-only `URLSearchParams`; read with `.get()` and serialize with `.toString()`. It does not mutate params. It may require a Suspense boundary during prerender/build; current order workspace is already client rendered under the app shell. Do not use this hook in a Server Component layout.
- `03-api-reference/03-file-conventions/page.md`: Server Component pages can receive the asynchronous `searchParams` prop; current `/app/[section]/page.tsx` already treats `params` as a Promise. If choosing server parsing, pass normalized values to the client workspace. Client component hook is the smaller fit for present architecture.
- Preferred implementation shape: initialize filter/page/selection from `useSearchParams`, make a fresh `URLSearchParams(searchParams.toString())` before writing, use `router.replace('/app/orders?...')` for search/status/page so each keystroke does not create an unusable history entry (debounce search), and use `router.push` for open detail / create mode so Back closes the object. Keep URL normalization deterministic and omit defaults. On Back/Forward derive state from current search params; do not mirror stale URL values in unrelated local state. Verify direct deep link and reload.

## Suggested Fiori-style screen structure

- Overview becomes an actionable worklist: compact exception counts, priority rows grouped by due/age/severity, source identifier and cause, and one relevant action per row. Use stable details page links and explicit loading/error/empty states.
- Orders becomes a list report with search/status/page in URL. Detail selection becomes a URL-addressable object page with header status/value/customer, line items, transition history, audit link, and Draft-only Edit/Confirm/Cancel actions. Edit can reuse the same form fields in a detail mode and existing PATCH.
- Inventory becomes SKU list report with explicit stock columns; selecting a SKU opens an object page with balance summary, confirmed reservation orders, stock movements with source document links, low-stock history, and audit events.
- Receipts becomes document list report (receipt number, supplier, date, line count/quantity, actor) and object page (header, supplier, lines, linked movements, audit). Keep `Receive stock` as an action.
- Preserve existing semantic tokens, responsive tables/cards, keyboard/focus patterns, unsaved-change guards, RBAC, and command recovery. The user-selected direction is cool bright background, navy structure, restrained decoration.

## Minimal contract and API changes by scope

1. **Actionable exception worklist:** extend `OverviewResponse` in `packages/contracts/src/analytics.ts`; compose a bounded items query in `apps/api/src/dashboard/dashboard.service.ts`, preserving tenant transaction and `inventory:read` policy or splitting permissions only if current role semantics require it. Web owns presentation in `overview-workspace.tsx` and its API adapter. Prefer detail links to existing objects.
2. **Order UX and recovery:** no new list/detail/edit schema needed. Web owns `features/orders/api.ts`, `orders-workspace.tsx`, `components/order-detail-view.tsx`, form reuse/edit state, and URL state. API idempotency requires `orders.controller.ts`, `orders.service.ts`, and possibly OpenAPI docs/tests; contracts likely unchanged for create payload/response. Keep edit and create separate command intents/scopes.
3. **Receipt documents:** API owns new GET list/detail route, query/service/mapper and shared receipt detail/list schema in inventory contracts/OpenAPI. Web owns receipt API, receipts workspace, receipt object page and links. Avoid reuse of movement rows as document records.
4. **Reservation/source/audit trace:** API owns reservation query/contract and adding optional audit `entityId` filter (unless link can use filtered `entityType` only). Web inventory object page owns source navigation. Existing movement source refs need no DB change. Receipt detail response can include `movementIds` or movement rows via `referenceType/referenceId` query.
5. **Fiori shell/shared components:** one integration owner should own app shell/navigation and shared worklist/object-page primitives plus shared styling. Feature workers should not edit these concurrently.

## Safe parallel ownership split for implementation

Parallel workers can proceed with non-overlapping paths after agreeing on contract names and URL parameter names:

- **Orders worker:** `apps/web/features/orders/**`; API idempotent-create edits in `apps/api/src/orders/**` and its corresponding tests/OpenAPI entries. Do not change shared shell, global UI primitives, or overview contracts.
- **Receipt worker:** `apps/api/src/inventory/**` receipt query/route plus receipt schemas under `packages/contracts/src/inventory.ts` and focused API tests; web `apps/web/features/receipts/**`. Coordinate shared inventory contract edits with reservation work before editing the same contract file.
- **Overview exceptions worker:** `apps/api/src/dashboard/**` and overview response contract `packages/contracts/src/analytics.ts`; `apps/web/features/overview/**` and focused tests. Keep exception detail links aligned with object-page URL conventions agreed with Orders/Inventory/Receipts owner.
- **Inventory/reservation worker:** inventory reservation query/API and shared contract addition; web `apps/web/features/inventory/**`. Coordinate the inventory contract file with Receipt worker. Avoid concurrent edits to app shell or audit contract.
- **Shell/integration owner:** `apps/web/components/app/**`, shared UI components/tokens, and any shared route helper/object page primitive. Integrate feature work after parallel branches land. Own `useSearchParams` parsing helper if shared; otherwise each feature can locally own URL encoding.

Do not assign the same shared contract file to separate workers at the same time. Safest sequence: one integrator creates/merges the contract/API names first, then assigns Overview, Orders, Receipt, and Inventory UI in separate directories. API tests should cover tenant scoping and permission boundaries for every newly composed read.

## Verification cases for a plan

- **Overview:** each exception row displays a real item and cause, links to its exact object, and action routes to a usable handling screen; zero counts show a useful empty state; tenant scoping and relevant permissions are honored.
- **Orders:** list URL includes search/status/page; reload preserves these and `?order=<id>` opens the same object; Back/Forward opens/closes or restores the right object; Draft edit loads customer/line/note values and PATCH saves; after another actor confirms, edit receives a conflict and the user sees refreshed current status; non-Draft hides edit.
- **Create recovery:** simulate server commit then lost response, reload, retry same key/payload, and assert exactly one order, same ID/response, one create audit, and no duplicate lines. Different payload with same key is a conflict. Expired recovery tells user to verify and blocks replay.
- **Receipt documents:** two receipts with multiple lines appear as two documents; search/filter/page work; document detail shows supplier, receipt number/date/note and all lines/costs; source movements and audit link resolve; receipt document list/detail enforce tenant scope and `inventory:read`/receipt visibility.
- **SKU trace:** balance total reconciles to confirmed order reservations; each reservation opens the matching order; each receipt/sale movement opens its source document; adjustments show their reason; per-entity audit deep link returns only matching entity. Cancel and fulfill update current reservations and retain history.
- **Navigation/design:** responsive narrow and desktop layouts support list report/object page transitions, browser history, focus return, keyboard interaction, unsaved-edit warning, loading/error/empty states, RBAC and existing command recovery.

## Confidence and remaining gaps

- **High confidence:** route presence/absence, current exposed fields, UI state model, order update transaction and movement references; established by source lines cited above and contracts.
- **Medium confidence:** best endpoint shape for a single exception worklist and reservation breakdown. Both are recommendations based on current data model, permission rules and UI needs; confirm permission matrix before composing events from modules with different read permissions.
- **Needs follow-up before implementation:** confirm whether product/object-page routes should be query-selected within section pages or new nested routes; decide whether the exception API should expose `salesOrderId` for failed deliveries where present; check generated OpenAPI route snapshots when adding receipt GETs; verify test harness patterns before choosing integration tests.
