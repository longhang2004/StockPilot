## Delivered API contracts

- `GET /v1/receipts?page=1&pageSize=25&search=` returns a tenant-scoped page of receipt documents, newest `receivedAt` first, with supplier identity, `lineCount`, and `totalQuantity`. Search matches receipt number or supplier company name. Page size is bounded to 100.
- `GET /v1/receipts/:id` returns the same document summary plus stable receipt lines with product name/SKU and nullable unit cost. Receipt rows have `createdAt` and `receivedAt`; they do not have an `updatedAt` column. Missing and cross-tenant IDs return 404.
- `GET /v1/inventory/products/:id/trace?reservationsPage=1&reservationsPageSize=25&movementsPage=1&movementsPageSize=25` returns `{ product, balance, reservations, movements }`. `balance` is nullable and includes on-hand, reserved, available, warehouse, and update time. Reservation rows represent only current `CONFIRMED` sales-order lines; each row's stable `id` is the `SalesOrderLine.id` and it includes `orderId`, order number, customer name, quantity, and confirmation timestamp. Movements retain the existing ledger shape and include product identity and source references. Reservation and movement page sizes are independent and each capped at 100. The read runs in `RepeatableRead` to keep its balance and line snapshots consistent; no write transaction isolation was changed.
- `GET /v1/inventory/movements` now accepts optional UUID `productId` so a SKU detail page can link to its ledger independently.
- `GET /v1/audit-events` accepts optional UUID `entityId` alongside existing `entityType` and pagination.
- `POST /v1/orders` accepts optional `Idempotency-Key` for compatibility with clients already on the old API. First-party clients should always send it. A supplied key replays the original 201 response for the same tenant/scope/payload for the existing 24-hour idempotency window; a different payload under the same key returns 409. Requests without the header keep the legacy create behavior.

Shared Zod/OpenAPI contracts are in [inventory.ts](../../../packages/contracts/src/inventory.ts#L126). Controller routes and response bindings are in [inventory.controller.ts](../../../apps/api/src/inventory/inventory.controller.ts#L96), [inventory.controller.ts](../../../apps/api/src/inventory/inventory.controller.ts#L220), and [audit.controller.ts](../../../apps/api/src/audit/audit.controller.ts#L24). Draft create's compatibility contract is in [orders.controller.ts](../../../apps/api/src/orders/orders.controller.ts#L99). The existing POST receipt response schema was corrected to match the actual Prisma serializer: `ReceiptResultSchema` no longer claims the model has `updatedAt`.

## Implementation ownership and behavior

- API and contract ownership: `packages/contracts/src/inventory.ts`, `apps/api/src/inventory/**`, `apps/api/src/audit/audit.{controller,service}.ts`, `apps/api/src/openapi/schemas.ts`, `apps/api/src/orders/orders.{controller,service}.ts`, plus the matching receipt/order/OpenAPI tests.
- Read models in `inventory-query.service.ts` always scope product, receipt, line, movement, and reservation queries to the authenticated organization. Trace reservations come from current confirmed order lines; no synthetic reservation movement is written and inventory ledger arithmetic is unchanged.
- `TenantDatabase.withTenant()` accepts optional Prisma transaction settings. Only product trace opts into `RepeatableRead`; other query and write paths retain default behavior.
- The existing idempotency service provides organization/scope/key advisory locking, canonical payload fingerprinting, persisted status/body, and conflict behavior. Draft create uses scope `order:draft:create` inside the tenant transaction.
- Integration tests cover receipt search/grouping, two-document pagination, multi-line total, detail identity, own-tenant visibility and foreign-tenant 404/empty search; response schema parsing; receipt source movement/audit links; current reservations against balance before fulfillment and their removal after fulfillment/cancellation; sale movement source link; concurrent keyed Draft create replay, one audit event, changed-payload 409; old no-key creates; and OpenAPI route/schema/header publication.

## Frontend handoff

Frontend can use the contracts now. Use the `ReceiptDetail` contract as written (no `updatedAt`), `InventoryProductTrace` for SKU source/availability detail, and `entityId` for audit filtering. Draft-create UI should create its key before the first POST and persist/reuse it across uncertain retry; do not generate a new key for the retry. For URL-backed list state, existing orders API accepts `page`, `pageSize`, `search`, and `status`.

The backend worker has not committed or pushed implementation source. The planning checkpoint alone is published. This file is a progress handoff, not completion of the overall redesign.
